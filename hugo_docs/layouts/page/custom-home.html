Architecture Agents Screener Tools API Docs

GO 1.25.7 · GIN · LANGCHAINGO · GPT-5.6 LUNA · ARANGODB · REDIS

A multi-agent, multimodal, high-concurrency agentic engine for Indonesian equity-market workloads.

Every turn is planned before it runs: a plan-and-execute pipeline selects tools from a registry of thirty, executes each one once, and routes the result to one of two agents — a streaming synthesiser or a one-shot customer-service manager. A turn may carry images, which ground the planner, the tools and the final answer alike. In front of the queue sits a cache fast-lane for repeat questions; behind it, a per-request event bowl keeps the stream resumable when the client's connection drops.

50 concurrent requests 5 LLM stream workers 100-deep FIFO queue 30 registered tools 3 images per turn
Agentic engine · request lifecycle
Entry Admission authz · limits · cache key
Tier 1 Cache fast-lane dedicated workers · no semaphore
Tier 2 Queue + semaphore strict FIFO · one promotion path
Tier 3 Plan → agents → stream dual-agent · resumable

The cache fast-lane runs on its own workers and never takes the processing semaphore, so a repeat question is answered while the queue stays untouched. A miss falls through to the queue. Image turns skip the lane entirely — they are never read from or written to the cache.

ARCHITECTURE

System Architecture

One FIFO queue gated by a single processing semaphore, with a cache fast-lane in front of it and a per-request event bowl behind it. Admission, preparation, tool execution and LLM synthesis are separate stages, each with its own concurrency bound, so a slow model cannot starve the intake path. The bowl decouples the stream from the HTTP connection that started it, which is what makes resume possible and minimises the cost of a client dropping mid-answer.

AGENTS & MODALITY

Multi-Agent Routing & Multimodal Input

A single planning call classifies the turn, plans the tool DAG, and emits three understanding booleans — and then the server, not the model, derives which agents answer. Tools execute once and feed both agents, so the customer service manager reviews the analyst's finished output rather than repeating its work. Image attachments follow the same discipline: one context injection point, one canonical read gate, and five LLM call sites that ground on the pixels.

TOOLS

Tool Catalog

Thirty tools are registered in a single data-driven registry, tools/toolcore/definitions.go. They span market data and prices, broker and order flow, company research, financial reports and ratios, screening and rankings, sectors and investment concepts, mutual funds, signed-in user context, and knowledge retrieval. Each entry carries a name, an LLM-facing description, a JSON schema, and an executor; there is no second registry.

  • historical_marketdataHistorical price series for one stock between two dates at a chosen granularity, from daily to yearly.

Financial Reports

Orchestration & special handling

  • compare_stocksNot a registered tool. It is a reserved terminal synthesis marker the planner may emit; the pipeline marks it direct-stream intrinsically, by name, and routes it to the comparison synthesiser in chatbot/processing/comparison.
  • Plan modesEvery turn is classified as simple (all tools fire in parallel, no dependencies), pipeline (ordered steps where later steps consume earlier output), or fixed_answer (canned response).
  • Step executionWithin a pipeline step, execution is either single or map. A map step runs one tool once per item of an upstream array, typically the stock codes from a generator step.
  • AggregationModeA per-step boolean, not a fourth plan mode. It marks a terminal step that executes no tools and instead concatenates every prior step's output for the synthesising LLM.
  • Concurrency & retriesDEFAULT_PARALLEL_LIMIT bounds in-flight tool calls, DEFAULT_RETRY_LIMIT bounds per-step retries, and MAX_TOTAL_STOCKS_FOR_MAP_EXECUTION caps the fan-out of a map step.
  • DISABLED_TOOLSDropped from the registry at build time, so the LLM never receives the schema. Validated at startup.
  • TIMEBOUND_TOOLSTools whose output is inherently time-sensitive. Any turn whose plan touches one is never response-cached.
  • USERBOUND_TOOLSPer-user tools. Also disable response caching, since a shared cache would leak one user's data to another, and are excluded from lossy summarisation.
  • EXCLUDE_TOOLS_FROM_CITATIONOutput is tagged so the synthesiser emits no [source_N] reference. Private user data and RAG answers have no citable public source. A dynamic registry additionally suppresses citation when a tool returned no usable data.
  • STOCK_CODE_GENERATOR_TOOLSThe tools that produce a list of stock codes and can therefore feed a downstream map step. Only these may legally occupy step_1 of a real pipeline.
  • TOOL_TIMEOUTPer-tool execution deadline.
  • MAX_LLM_INPUT_TOKENSCaps LLM input tokens. It drives fallback-extractor truncation, the aggregation-step input guard, and the target size for summarisation. It is not a per-tool output cap.
  • NATURAL_ANSWER_TOOLSExists in code but defaults to empty and is not set, so the optional direct-stream path for RAG answers is off. frequently_asked currently takes the normal blocking call plus LLM-synthesis path.

API

API Endpoints

A submit / stream / status / cancel lifecycle, plus session history, user settings, file assets, suggestion questions and operational routes. Every route is registered in internal/app/router.go.

Authentication

There are three tiers. RequireAuth guards the /chat, /session, /user, /files, /question and /v2 groups. It always requires an X-API-Key header. When DYNAMIC_AUTH=true it additionally requires a userId header and validates the pair against the credential service at BE_AUTH_URL; a beta-access check against BE_BETA_ACCESS_URL runs as well when BETA_ACCESS_CHECK=true. The validated userId becomes the caller identity for the rest of the request.

RequireStaticAuth guards the admin routes. It always validates the static X-API-Key and ignores DYNAMIC_AUTH, so it never establishes a per-user identity.

Public routes carry no header auth: the static assets (GET /, /style.css, /app.js, /favicon.png, /js/*filepath), /health, the four data-refresh routes, and the three SSE endpoints. The SSE endpoints are public by design — EventSource cannot set custom headers — so the unguessable request_id is the capability that grants access to a stream.

authz.EnforceOwnership is a second layer applied inside handlers for user-scoped resources. It compares the authenticated identity against the resource owner and returns 403 FORBIDDEN on a mismatch. Note that ownership is only enforced under dynamic auth: with DYNAMIC_AUTH=false there is no per-user identity, and every ownership check returns true.

Credential caching. With CACHE_VALID_CREDENTIALS=true and a Redis client present, the combined result of the auth call and the beta-access check is cached in Redis under a key derived from the user id and a SHA-256 digest of the token, so the token is never stored in the clear and a rotated token forces re-validation. Entries are fresh for VALID_CREDENTIAL_TTL (default 1h). Past that the credential is re-validated upstream; if the upstream service is unavailable, the stale entry is served within the VALID_CREDENTIAL_STALE_TTL grace window (default 24h). An explicit upstream rejection evicts the entry immediately.

Deployment requirement. PRODUCTION_MODE must be set to true in any deployed environment. When it is false the server additionally accepts a development credential, which is intended only for local work; under PRODUCTION_MODE=true that path is disabled and any attempt to use it is rejected and logged. The public operational routes below should also be restricted at the ingress layer in a deployed environment.

Chat lifecycle

  • POST/chat/submit(Auth + ownership) v1 submit. JSON only. message, user_id and conversation_id required; request_id optional and auto-generated. Returns 202 with a request_id.
  • POST/v2/chat/submit(Auth + ownership) Dual-agent, multimodal submit. Accepts multipart or JSON. request_id is mandatory; conversation_id is ignored and derived as default_<user_id>.
  • GET/chat/stream/:request_id(Public SSE) Main token stream for a submitted request. Emits 1 s heartbeats until the first real event.
  • GET/chat/cs_manager/answer/:request_id(Public SSE) One-shot CS-manager answer stream. Emits info → answer → info, or a single info with status: "not_selected".
  • GET/chat/resume/:request_id(Public SSE) Replays a turn whose SSE connection dropped. Returns 404 RESUME_DISABLED when USE_BOWL=false.
  • GET/chat/status/:request_id(Auth + ownership) Polls request state. Pins the legacy shape: cs_manager_generating is rewritten to formulating_final_answer and progress.selected_agents is stripped.
  • GET/v2/chat/status/:request_id(Auth + ownership) Same handler without the legacy pinning: keeps cs_manager_generating and progress.selected_agents.
  • POST/chat/cancel/:request_id(Auth + ownership) Cancels one in-flight request. 404 if the request is unknown.
  • POST/user/cancel/:user_id(Auth + ownership) Cancels every in-flight request for a user. 404 when the user has none active.
  • POST/chat/reaction(Auth + ownership) Sets a reaction on a completed turn. Body {request_id, reaction}.
  • POST/chat/feedback(Auth + ownership) Free-text feedback on a request. Body {request_id, feedback}, feedback capped at 10 000 characters.
  • GET/chat/sources(Auth + ownership) Footnote sources for a request. Query req_id (required) and lang (en/id/zh). Returns a numerically sorted list.
  • GET/chat/sources_map/:request_id(Auth + ownership) The same data as the raw {"source_1": …} map, avoiding the lexicographic ordering of the list form.

Session & history

  • GET/session/history(Auth + ownership) v1 history, keyed by the conversation_id query param. Optional n for the last N turns. Pins the legacy shape: dual-agent and image fields are nulled.
  • GET/v2/session/history(Auth + ownership) Single-session-per-user history keyed by the user_id query param. Supports n and a before cursor; returns next_cursor and has_more.
  • GET/session/:user_id(Auth + ownership) All of a user's sessions, grouped by date.
  • POST/session/title(Auth + ownership) Sets or LLM-generates a conversation title. Body {conversation_id, conversation_title, use_llm}.
  • DELETE/session/:conversation_id(Auth + ownership) Soft delete by default; query soft_delete=false for a hard delete. 409 ALREADY_DELETED if already gone.
  • GET/session/incomplete/:conversation_id(Auth + ownership) Lists requests still in flight for a conversation. Used by the client to decide what to resume.

/session/history and /session/:user_id share a path segment. Gin resolves the static segment first, so /session/history reaches the history handler and any other value reaches the session-list handler.

User & settings

  • POST/user/channel(Auth + ownership) Sets the user's channel. Body {user_id, channel}, both required.
  • GET/user/settings/:user_id(Auth + ownership) Preferred name, CS-manager persona and portfolio permission. Returns 403 ENDPOINT_DISABLED when ENABLE_CS_MANAGER=false. An absent document yields 200 with null fields, never 404.
  • POST/user/settings(Auth + ownership) Partial upsert of the same fields; cs_manager_person must be Luna, Kevin or Mia. Returns 403 ENDPOINT_DISABLED when ENABLE_CS_MANAGER=false.
  • GET/user/portfolio_access_permission/:user_id(Auth + ownership) Backward-compatible read of the legacy permission collection. Active regardless of ENABLE_CS_MANAGER.
  • POST/user/portfolio_access_permission(Auth + ownership) Backward-compatible write of the same legacy collection. New clients should use /user/settings.

Files

  • GET/files/image/:image_file_id(Auth + ownership) Streams the raw image bytes with Content-Disposition: inline and Cache-Control: private, max-age=3600. Ownership is checked against the stored asset's user_id. The route always exists but returns 404 NOT_FOUND while ENABLE_IMAGE_PROCESSING is off, so the flag can be flipped without a redeploy.

There is no voice route today. The handler is kind-generic and already rejects the voice kinds, so the voice epic adds a route rather than a new code path.

Suggestion questions

  • POST/question/generate_for_welcome_page(Auth + ownership) Generates exactly five welcome-page questions. Body {user_id, entry, entry_stocks, lang, is_refresh}; entry_stocks holds at most two unique codes.
  • POST/question/generate_for_new_answer(Auth + ownership) Follow-up questions for a completed answer. Body {request_id, is_refresh, lang}. is_refresh=false serves the cached set; true regenerates via the LLM.
  • POST/question/record_click(Auth + ownership) Records a click for ranking. Body {question_id, api_source, suggested_questions_id}; api_source is welcome_page or new_answer.

Admin

  • POST/stats/daily(Admin) Daily chat counts from start_date (default yesterday) through yesterday. Gap days are filled with zeros; the response also carries a true distinct-user count over the range.
  • POST/question/overwrite_data(Admin) Uploads an .xlsx of question templates as multipart part file, at most 10 MB. Replaces the in-memory templates and persists a new overwrite id.
  • GET/question/get_click_stats/:question_id(Admin) Click statistics for one question id. 404 when there is no record.

The /v2 surface

Three routes carry a /v2 prefix. They are the breaking variants of the endpoints whose request or response contract changed for the dual-agent and multimodal work; the unprefixed paths stay legacy-shaped for un-migrated clients. All three always exist — dual-agent content appears only when ENABLE_CS_MANAGER=true.

POST /v2/chat/submit accepts multipart/form-data as well as plain application/json. In the multipart form the JSON body goes in a part named payload, and one or more image attachments go in repeatable parts named image_file. A missing or unparsable payload part is a 400. Image parts are silently ignored when ENABLE_IMAGE_PROCESSING is off, which keeps flag-off behaviour identical to the JSON path. message is optional when at least one image is attached.

GET /v2/session/history surfaces image_file_ids on each item, alongside tuntun_ai_output, cs_manager_output, cs_manager_person, selected_agents and reply_to. The v1 history endpoint nulls all of these.

The submit payload:

{
  "message": "How did BBRI perform last quarter?",
  "user_id": "user-123",
  "conversation_id": "conv-456",
  "request_id": "req-789",
  "lang": "en",
  "is_event": true,
  "event_metadata": {
    "stock_code": "BBRI",
    "event_title": "Quarterly earnings release",
    "event_detail": "Q3 results published",
    "event_type": "earnings",
    "occurred_at": "2026-01-07"
  }
}

is_event defaults to false. When it is true, event_metadata must be present with all five fields non-empty and occurred_at in YYYY-MM-DD form; this validation applies on both v1 and v2. /v2 additionally accepts reply_to, cs_manager_person and preferred_name.

Streaming events

All three SSE endpoints frame events as data: <json>\n\n. Every event is a {type, payload} envelope, and there are exactly five types: info, token, error, heartbeat and answer.

token and error carry a bare JSON string. heartbeat carries no payload. answer appears only on the CS-manager stream. info is overloaded: the same event type carries first-token timing and provenance, terminal completion, cancellation, dual-agent signalling, and plain informational strings — a consumer must branch on the payload shape. 

data: {"type":"token","payload":"BBRI "}

data: {"type":"info","payload":{"timeToFirstToken":0.84,"source":"llm","tools_used":2}}

Request states

The status endpoints report one of:

  • submittedQueued. Note the divergence: the Go identifier is StateQueued but it serialises on the wire as "submitted".
  • choosing_toolsFirst LLM call, selecting tools.
  • calling_toolsExecuting the selected tools in parallel.
  • formulating_final_answerSecond LLM call. Skipped on the direct-RAG path.
  • ready_to_streamFirst token produced; streaming has started.
  • task_executionTask execution in progress.
  • fastlane_processingThe cache fast lane is serving the turn.
  • cs_manager_generatingCS-manager answer being generated. Only surfaces on /v2/chat/status; the v1 path rewrites it to formulating_final_answer.
  • completedTerminal. Every completed_* completion status collapses to this.
  • cancelledTerminal. Cancelled by the user.
  • erroredTerminal. Failed with an error.

not_selected is a related constant but is not a status-endpoint value — it only ever appears as the status field inside an SSE info payload, signalling that an agent was not routed to.

Response codes

Submit returns 202 Accepted on success, with data.status set to "submitted". Two non-error outcomes return 200 instead: data.status: "usage_limit_exceeded" when the daily limit is reached, and data.status: "already_exists" when the request_id is a duplicate that cannot be reprocessed. Clients must branch on data.status, not on the HTTP code alone.

Almost every JSON endpoint wraps its result in the same envelope:

{
  "status": 0,
  "errorCode": null,
  "message": "success",
  "traceId": "…",
  "data": { }
}

status is 0 on success and an HTTP-like code on failure; errorCode is null on success and a stable string such as BAD_REQUEST, NOT_FOUND, FORBIDDEN, ENDPOINT_DISABLED or AUTH_UNAVAILABLE on failure. The exceptions are the image download (raw bytes), the SSE endpoints (text/event-stream) and the four data-refresh routes (raw stats struct).

Docker Compose

Five compose files ship with the repo. They differ in what is treated as external:

  • docker-compose.yml — the full local stack. Everything runs in-tree.
  • docker-compose.local.yml — the same stack with Redis published on host port 6379 instead of 6380.
  • docker-compose.staging.yml — staging; the app is published as 8080:8080 on a bridge network rather than host networking.
  • docker-compose.cd.yml — the CD deploy. App container only, plus the dummy backend, the backup daemon and observability. Redis and ArangoDB are external.
  • docker-compose.db.yml — Redis and ArangoDB only, for running the app on the host with go run main.go.

The full stack starts:

  • redis — redis/redis-stack, published on 6380 (container 6379). Persistence is deliberately left in the ephemeral layer so the cache resets on deploy.
  • arangodb — published on 8529, plus a backup-daemon container running run_daily_backup.sh.
  • chatbot-app — network_mode: host, API_PORT=8080, reading .env plus an optional .prod.env.
  • loki — 3100.
  • grafana — 3000, with datasources and dashboards provisioned read-only from ./grafana/provisioning.
  • vector — no published port; it tails the Docker socket and ships container logs to Loki.

Every app-running compose file mounts the named volume file_assets_data at /app/data/file_assets and sets FILE_STORAGE_ROOT to that absolute path. This matters: image metadata lives in ArangoDB but the bytes live on local disk, and the container WORKDIR is /root, so the relative default ./data/file_assets resolves inside the container layer. Without the volume every upload is destroyed on redeploy while the session history keeps advertising the file ids.

Do not run docker compose down -v against these files — it deletes the ArangoDB volume.

Manual local setup

  1. Clone the repo and cd into it.
  2. Fetch dependencies: go mod tidy.
  3. Configure .env.
  4. Start Redis and ArangoDB — either your own, or the pared-down compose file.
  5. Run the app.
docker compose -f docker-compose.db.yml up -d   # Redis 6379 + ArangoDB 8529

The process binds exactly one listener, API_HOST:API_PORT. The development .env uses 8082; the Docker stack sets 8080. API_HOST is absent from .env and falls back to its default 0.0.0.0. Health lives at GET /health on that same port — there is no separate health listener.

There is no Makefile. The shell scripts at the repository root are the entry points.

Service discovery

Most BE_* variables are not plain HTTP URLs. They take the form consul://<service>/<path> and are resolved at call time by tools/toolutils/consul.go, which picks a healthy instance and rewrites the URL before the request goes out. Resolution retries up to CONSUL_RESOLVE_MAX_ATTEMPTS times with CONSUL_RESOLVE_RETRY_DELAY between attempts, and successful lookups are held in an in-process cache for CONSUL_RESOLVE_CACHE_TTL to minimise agent round-trips. The cache self-heals: when a request against a cached address fails, that entry is evicted so the next call re-resolves rather than repeatedly dialling a dead instance. Setting the TTL to zero or below disables caching entirely.

Note that CONSUL_ENABLED defaults to false and is absent from the development .env, while nearly every BE_* URL there is a consul:// URL. Local runs that need real backend data must set it explicitly.

TESTING

Usage & Testing

182 test files across the tree. The suite is run sequentially, on purpose.

Running the application

go run main.go

The listen port comes from API_PORT — 8082 in the development .env, 8080 under Docker.

The canonical test runner

./run_package_tests.sh

This runs 18 packages one after another, each preceded by go clean -testcache: ./chatbot, ./chatbot/bowl, ./chatbot/cache, ./chatbot/cancellation, ./chatbot/helpers, ./chatbot/processing, ./chatbot/queue, ./db, ./core, ./chatbot/files, ./chatbot/processing/comparison, ./internal/context, ./internal/handlers, ./types, ./config, ./tools/toolcore/planner, ./tools/tooltypes, ./tools/toolnonbe.

It is deliberately not go test ./.... Several of these packages truncate the same shared ArangoDB database, tuntun_chatbot_test, as part of their fixture setup. Go's default behaviour is to run distinct packages in parallel, so under ./... they clear each other's rows mid-test and fail in ways that look like application bugs. Listing the packages and running them in sequence removes the shared-state race; the script's own comment records that a roughly 35% flaky test in chatbot/processing/comparison stayed hidden for an entire epic because that package was not on the list.

Note the coverage gap this creates. Packages that are not listed — including tools/tooltest, tools/toolbe, tools/toolutils, tools/toolcore/pipeline/* and chatbot/usage — have tests but are not exercised by the canonical run.

Scale

182 *_test.go files. The heaviest packages are internal/handlers (15), chatbot (12), tools/toolcore/pipeline/execution (10), chatbot/helpers (10) and chatbot/processing (9).

Other scripts

  • ./run_main_tests.sh — the root package (main_test.go, stream_test.go, test_helpers_test.go), then ./internal/..., then ./cmd/test_status/integration.
  • ./run_tool_tests.sh — the tools subsystem, with per-test pass/fail accounting instead of failing fast.
  • ./run_cache_tests.sh — sources .env, requires REDIS_URL and LOG_DB_TEST_NAME, then runs chatbot/cache under -race plus the fast-lane integration steps.
  • ./run_deployment_tests.sh — requires a running server. Drives cancel/resubmit, HTTP-disconnect, /resume, /status, session and title-generation flows against it.
  • ./cmd/run_healthcheck.sh <prog.go> — builds and runs one external-API health-check program, then cleans up. Example: ./cmd/run_healthcheck.sh tools/tooltest/extapi/valuation.go.
  • ./cmd/benchmarks/run_*_benchmarks.sh — eight benchmark runners: bowl, cache, cancellation, critical, manager, processing, queue, tool.
  • ./cmd/dlv/*.sh — Delve helpers (dlv_core.sh, dlv_test.sh, dlv_trace.sh).

CI caveat

The package_tests job in .gitlab-ci.yml runs ./run_package_tests.sh and is marked allow_failure: true. A green pipeline therefore does not mean the tests passed — it only means the blocking jobs, chiefly the gitleaks secret scan, passed. Read the published package_test_results.xml JUnit artifact rather than the pipeline badge.

Two related notes. config.LoadForTest walks up to the project root and loads the real .env, so unit tests inherit developer credentials locally; CI overrides LOG_DB_URL and REDIS_URL through job variables. And CI_CD_TEST=true makes Redis-dependent tests skip instead of fail when Redis is unreachable.

Adding a new tool

  1. Implement the logic. Put it in tools/toolbe/ if it calls a backend service, or tools/toolnonbe/ if it is self-contained.
  2. Register it. Add a DynamicTool literal to one of the themed builder functions in tools/toolcore/definitions.go. BuildAllTools concatenates those builders into the single registry, so nothing else needs editing: the planner prompt, executor and citation layers all read from it.
  3. Add a schema. If the arguments do not match an existing shape, declare a reusable one in tools/toolcore/schemas.go and reference it from the definition.
  4. Add a test. Write a suite under tools/tooltest/, and a live health check under tools/tooltest/extapi/ if the tool talks to an external API.
  5. Check the config lists. A new tool may need listing in TIMEBOUND_TOOLS (never serve a cached answer), USERBOUND_TOOLS (scope the cache key per user), EXCLUDE_TOOLS_FROM_CITATION, or STOCK_CODE_GENERATOR_TOOLS. DISABLED_TOOLS removes it from the registry at startup without a code change.

The two-phase workflow

Code changes go through two separate sessions. /analyze traces the dataflow for a target, entry point to exit point, and writes an analysis file recording the current structure with real file paths and line numbers; it proposes nothing. /implement then takes that file as ground truth, creates a task in the nearest .workflows/todos.md, writes a plan with complete code, and executes it. Splitting the two keeps exploration tokens out of the implementation context. Plans are local artefacts and are gitignored by design.
